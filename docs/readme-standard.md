# README 写作规范

> 目的：README 是项目的"对外合同"。里面的每个数字、每个开关、每条能力边界，
> 都必须能在当前代码里找到依据。**过时的 README 比没有 README 更伤信任。**

本规范同时由 [`scripts/check_readme.py`](../scripts/check_readme.py) 自动校验，
CI 里跑不过就不允许合并。

## 1. 必须包含的章节（按此顺序）

| 章节 | 必须写清什么 |
|---|---|
| 标题 + 一句话定位 | 这个项目**给谁**解决**什么**问题（不要写"基于 XX 的 YY 系统"这种无信息量的话） |
| 徽章 / 关键数字 | 测试数、许可；数字必须与代码一致 |
| 痛点 → 解法 | 先讲使用者的处境，再讲项目怎么解 |
| 核心能力表 | 每行 = 能力 + 实现要点 + 用户可感知的结果 |
| 快速开始 | 三条命令以内能跑起来，且**已验证可执行** |
| 架构 | 数据流 + 目录结构；只画真实存在的模块 |
| 测试与评测 | 指标 + 复现命令 + 样本量 + 已知偏差 |
| 设计取舍与局限 | 主动写短板（这是可信度的来源） |
| Roadmap | 已做 / 待做分开，已完成项要给证据 |
| License + 数据来源 | 许可证与第三方数据授权 |

## 2. 数字规范

1. **每个数字都要能在仓库内复现**：指标给命令（`python -m app.eval_expert` 等），
   规模给查询（`SELECT COUNT(*) …`），不要在文中凭空写。
2. **标注口径与时间**：是"线上实例"还是"仓库演示快照"？是 p50 还是平均？
   例：`底库 47,678 位学者（线上实例，2026-11-05）`。
3. **数字格式固定**，便于机器校验：
   - 测试数：徽章 `tests-<N>%20passed` + 正文 `<N> 项测试`
   - 端点：`<N> 个端点`
   - 视图：`<N> 视图`
4. **性能数字必须来自实测**，并注明方法（多少条、几次、是否含缓存命中）。

## 3. 能力边界规范

- 任何**默认值**（如 `ST_AUTO_EXPAND=1`、`ST_CACHE_TTL=86400`）必须与代码一致，
  并写出对应的环境变量名，读者能自己去关。
- 任何**降级路径**（LLM 不可用、重排模型缺失）必须明说会发生什么。
- 不要写"高可用/生产级/企业级"这类无证据的形容词；要写就给出对应证据（压测、SLA、审计）。

## 4. 禁止项

- ❌ 未实测的性能数字（"毫秒级响应"）
- ❌ 与代码不一致的默认值 / 开关名
- ❌ 把未来计划写成已完成
- ❌ 把评测样本量藏起来只报百分比
- ❌ 截图与当前 UI 不符

## 5. 更新触发条件（改代码时必须同步改 README）

| 改动 | 要更新 |
|---|---|
| 增删测试 | 徽章、`N 项测试` |
| 增删端点 | `N 个端点`、端点表、目录结构里的数字 |
| 增删前端视图 | `N 视图` |
| 改默认环境变量 | "设计取舍"里对应的描述 |
| 改检索/Agent 指标 | "测试与评测"表 + 复现命令 |
| 完成 Roadmap 某项 | 移到"已完成"，并附验证方式 |
| 改部署方式 | 快速开始、`DEPLOY.md` |

## 6. 发布前检查清单

```bash
python scripts/check_readme.py     # 数字一致性（CI 也会跑）
bash scripts/setup.sh --check      # 快速开始是否仍可执行（可选）
```

- [ ] 快速开始三条命令，在干净环境里跑通过
- [ ] 所有数字与 `check_readme.py` 一致
- [ ] 默认值与 `.env.example` 一致
- [ ] 局限一节仍在说真话（本轮修的 bug 有没有改变结论？）
- [ ] Roadmap 里"已完成"的每一项都有可复现证据
- [ ] License / 数据来源仍在

## 7. 写作风格

- 中文正文，英文专有名词保留原文（OpenAlex、FTS5、RRF）。
- 先结论后依据；能一句说清就不写两句。
- 用**具体**代替**形容**：不写"效果显著"，写"R@10 86.0%，较基线 +7.5pt"。
- 承认失败也要写：负结果（"扩充净收益未确立"）比选择性汇报更可信。
