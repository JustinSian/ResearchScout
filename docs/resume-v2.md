## 项目描述

**ScholarTrust · 学术专家知识库与可信尽调 Agent**（个人项目，2026）

后端基于 **FastAPI + ASGI** 构建高性能服务，围绕"学术专家尽调"这一复杂任务实现 **Agent Harness**
运行时能力层，包含任务规划、虚拟文件系统、子 Agent 委派、上下文管理、可插拔中间件、
Skills 技能系统与全生命周期记忆。主 Agent 根据用户目标生成任务清单并持续追踪执行状态，
将专家召回、指标核算、事实核验等任务委派给 researcher / analyst / verifier 等专业子 Agent；
通过虚拟文件系统管理全量成果档案、尽调报告与核查快照，结合 **SQLite 短期上下文 + 档案快照
长期经验沉淀**，形成从"问题输入 → 证据检索 → 交叉核验 → 报告生成"的闭环。
数据侧自建可信采集与准入门槛（四组加权证据 + 复核队列），检索侧实现 **BM25 + 向量 + RRF/DBSF
融合**并建立双 gold set 评测，问答侧以交叉编码器实现可解释拒答与库外网络兜底。

**技术栈**：Python / FastAPI / LangGraph / SQLite(WAL+FTS5) / bge-small + bge-reranker(ONNX) /
Canvas 前端 / Cloudflare Tunnel

## 核心实现

- **任务规划与状态机**：把"比较两位专家""找审稿人"等目标拆成 6~7 步可执行子任务，
  维护 `pending / running / done / failed` 状态与每步产物，落库 `tasks / steps / spans` 三张表；
  规划器为确定性规则（意图可枚举），支持零延迟、可单测、可解释，避免规则不可控的幻觉。

- **虚拟文件系统与上下文管理**：抽象 `/dossiers/{pid}`、`/reports/{tid}`、`/agents/{role}`
  目录，支持读写、路径越界校验与产物回查；将大工具结果（单人 1,000+ 篇论文）落盘，
  主上下文只保留摘要与文件句柄，**上下文占用从 7.4KB 压到 254B（29.2×）**，长任务不再爆上下文。

- **子 Agent 委派与交叉核验**：主 Agent 按任务类型委派 researcher（多通道召回）、
  analyst（只读档案算 h-index / 主题分布，不碰检索避免被召回结果带偏）、verifier（逐条核对
  结论能否回溯到 pid/wid），各子 Agent 独立上下文、仅回结构化结论；verifier 曾识别出
  "同名不同人"（h-index 很高但研究方向为晶体结构），将其从审稿人推荐中剔除。

- **Multi-Agent 调度与仲裁**：构建 Supervisor 对 kb / task / web 三类 Agent 做能力探测与路由，
  仲裁时按来源分节标注、绝不混合证据；补齐"库内学术信息 + 外部最新动态"的混合问答
  （此前架构无法回答）。**路由准确率由 40% 提升至 90%（10 题留出集）**。

- **可信采集与准入门槛**：设计四组加权证据打分器（身份 / 产出 / 影响 / 归属），
  输出 score + verdict + reasons，`accept ≥ 0.80`、`review ≥ 0.50` 进复核队列且全链路留痕；
  人工抽检 60 条后修正对门槛的认知（三档均为真人，门槛实际作用是筛产出）；
  扩张期「网络背书」通道抽样 40 条，精度 **77.5%（95% CI 62.5%~87.7%）**，占比 2.8% 并可一键筛选。

- **混合检索与评测体系**：BM25(FTS5) + bge-small 向量 + RRF/DBSF 融合，全参数可切；
  构建"按被引排序 / 随机抽样"双 gold set，用 bootstrap 置信区间判定增益。
  **四次识破自身评测缺陷**：权威性先验存在标签泄漏（+74% 实为负增益）、摘要级与全文级 chunk
  融合仅在按被引真值上占优、自创"共享作者集合"指标大量误报，最终确立
  "**融合未跑赢更强单路则不启用融合**"的工程判据。

- **可解释拒答与库外兜底**：以 ONNX 交叉编码器判定"能否回答"（有答案 ≥0.858 / 无答案 ≤0.425，
  阈值 0.60），稠密与 BM25 分数无法区分；对库外问题路由至 AnySearch 公开网络检索，
  结果强制标注"未经本库核验"并保留原文链接，网络失败则降级为明确拒答，不做编造。

- **数据完整性治理**：通过图谱抽查发现作者-论文错位（根因：SQLite UPSERT 走更新分支时
  `lastrowid` 不刷新），全量重建 **48,935 条作者关联 / 88,611 条共著边**，
  抽样 12/12 与 OpenAlex 上游一致；将事故固化为六项健康检查（含 FTS 索引一致性），
  上线当天即发现 **6,567 名专家未进入搜索索引**并自动修复。

- **可插拔中间件与可观测性**：在工具调用、任务状态变更等节点注入 Hook，实现令牌桶限流、
  PII 脱敏（邮箱/手机号/长 ID）、审计落库与成本核算；`/trace/{tid}` 可回放每步耗时与产物，
  `/audit` 输出单任务成本（示例：6 步 / 10.3 成本单位 / 0 失败）。

- **Skills 技能系统**：将"审稿人匹配 SOP"、打分权重、领域校验阈值外置为 Markdown 技能，
  按渐进式披露分两层加载（索引 → 正文）；**修改权重文件即可改变排序结果，无需改代码**，
  并记录版本与失效场景，实现口径复用与演进。

- **全量成果档案（Dossier）**：以 OpenAlex author id 拉取全量成果，构建
  `dossier / dossier_work` 表并派生 h-index、近五年产出占比、高频期刊与主题迁移；
  **102 位专家共 23,242 篇论文（人均 228 篇，改造前全库人均 1.7 篇）**，
  支撑"方向差异对比""审稿人匹配"等需要完整成果的任务。

- **全生命周期记忆**：短期上下文（任务内虚拟文件系统）+ 长期记忆（任务缓存 + 档案快照 diff），
  缓存带语料版本校验以避免旧结论；同一问题二次尽调 **2,246ms → 50ms（45×）**，
  档案变更可输出"作品 +3 / h-index +1"级别的 diff。

- **前端与工程约束**：单文件 SPA（无构建）实现专家墙、专家画像、Canvas 力导向合作图谱
  （人/机构两层、三种着色、最短合作链）、Agent 流式问答、尽调任务流与复核队列；
  在**无 docker / 无 GPU / 无 sudo** 的机器上以 SQLite + 本地 ONNX 完成全部能力，
  检索压测约 20 rps、图查询 146 rps，并修复无鉴权写接口（改为 X-API-Key + fail-closed）。

## 业务价值

- **把"专家尽调"从人工翻页变成可复核的报告**：输入一句自然语言，6 步内产出带证据链的对照
  报告（全量论文数、h-index、近五年方向、代表作），每个数字可点回 pid/wid，评审可直接抽查。

- **让"专家库"可信且可控**：专家墙的每一个入榜者都有可审计的分数与理由，
  网络背书人群仅占 2.8% 且可筛选/可关闭；健康检查自动化后，数据事故从"用户投诉才发现"
  变为"上线当天自动暴露"。

- **在一台普通服务器上跑通全链路**：无 docker/GPU/外部向量库依赖，单机支撑
  47,569 位学者、11,104 篇论文、101,414 条合作边的检索与多步问答，可直接部署演示。

## 面试可展开的三个点（备选，不写进简历）

1. **为什么不用向量数据库/图数据库**：没有 docker；且 1~2 跳、路径、机构聚合在 SQLite
   递归 CTE 上足够，真正的短板是"图上没有分析"，补的是 Louvain 社区、最短链、机构关系网。
2. **为什么 Agent 用规则规划而不是 LLM**：演示环境没有稳定 LLM；24 题回归中工具选择 95.8%、拒答 100%，
   每步可解释、可单测；代价是开放问题答不了——这是有意的取舍。
3. **最值得讲的一次纠错**：`lastrowid` 事故——829 篇论文作者错位，是我自己抽查合作者名单
   发现的；修完之后把"怎么发现"变成了六项健康检查，其中一项当天又抓出 6,567 条索引缺失。
