# M45：单 agent vs 多智能体——对照组与成本分解

## 为什么做这个

项目里"多智能体"一直只有叙述（supervisor 路由到 kb/task/web），没有"它比朴素实现更好"的证据。
这一轮补对照实验：**同一套 20 条 gold set，跑两条路径**。

| 组 | 实现 | 含义 |
|---|---|---|
| **single** | `agent.answer(q)` | 一个 agent、一次性规划、**所有工具都能用**（最朴素的实现） |
| **multi** | `supervisor.run(q)` | 先做意图路由（kb / task / web / hybrid），再交给对应子 agent |

质量判定复用 `app/eval_answers.check_answer`（同一套约束，不另设标准）。

## 成本口径（必须说清）

这个项目的答案链路里**没有 LLM**（规则 + 检索 + 模板），所以：

- **token 成本两边都是 0**，拿它对比会得出"多智能体不花钱"的假结论；
- 改用三个可测的量：**工具调用次数**、**端到端延迟**、**是否触发外部网络兜底**。

外部调用是真实成本（配额、延迟、可解释性），所以 `web_hit_rate` 是这里最像"钱"的指标。

## 结果

| 指标 | 单 agent | 多智能体 | 差值 |
|---|---|---|---|
| 答案通过率 | 85% | **100%** | **+15pt** |
| 工具调用总数 | 20 | 19 | −1 |
| 联网兜底率 | 20% | **15%** | −5pt |
| 拒答率 | 0% | 5% | +5pt |
| 延迟 p50 | 446.8 ms | **122.9 ms** | **−324 ms** |
| 延迟 p95 | 4437.8 ms | **1511.7 ms** | **−2926 ms** |

单 agent 未通过的 3 条：

```
refuse-quantum   （"找研究 quantum gravity phenology 的专家"）
refuse-poetry    （"谁研究 medieval icelandic poetry"）
clarify-no-ctx   （"那这些人里谁被引最高"，无上下文）
```

## 怎么解读（不要过度解读）

**+15pt 全部来自"该拒的拒、该问的问"，不是"答得更好"。**

- 单 agent 对库里没有的方向会走网络兜底，于是"答上了"——但按我们的规格（库里没证据就拒答）这是错的；
- 单 agent 对无上下文的指代会当成普通检索，0 结果后再联网；多智能体直接要求澄清。

**延迟优势来自"短路"**：supervisor 先判断意图，明确该拒/该澄清时立刻返回，
不进入检索与交叉编码器；单 agent 每次都要走完检索 + CE + 兜底。

**工具调用数几乎没变（20 vs 19）**：说明多智能体在这里没有引入额外的调用开销——
因为它省下的正是"先做一轮注定失败的检索"。

**必须承认的反面**：如果产品目标是"尽量给出答案"，单 agent 的 20% 联网兜底反而是优点。
这个对照证明的是**规格对齐**（该拒就拒），不是"多智能体更聪明"。

## 测试

`tests/test_ab.py`（4 项）：通过率/工具数/联网率/拒答率/失败 ID、延迟分位口径、
空输入、全失败。全量 **146 项**通过。

## 遗留

1. **没有 LLM 成本**是本项目的特性，不是通例——换成真 LLM 后必须补 token 记账，
   否则"多智能体更便宜"就是错的（通常更贵）；
2. 20 条用例偏少，且"拒答"类占了 5 条，对通过率的杠杆很大；
3. 没有做 **task 子代理** 的单独对照（task 内部还有 researcher/analyst/verifier 三角色），
   即"多智能体内部再拆"的收益未量化；
4. 延迟只测了单次，没有测并发下的差异。
