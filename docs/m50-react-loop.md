# M50：LLM 工具循环（ReAct）对照实验

## 做了什么

前两轮证明了"路由不需要 LLM"（m49）。这一轮补上另一半：
**让模型自己决定调几次工具、什么时候收尾**（ReAct / function calling），再和规则路径对比。

| 组 | 实现 | 行为 |
|---|---|---|
| rules | `supervisor.run` | 规则路由 → 调一个工具 → 模板作答 |
| loop | `app/loop_llm.py` | 模型看工具结果 → 判断够不够 → 再调 → 写答案 |

## 硬约束（否则会烧钱/跑飞）

```
max_steps    4 轮
max_calls    6 次工具调用        # 模型一次可能并行给多个 call，必须按 call 计数
budget_usd   $0.02 / 会话
timeout      60s / 轮
工具报错回灌给模型（让它自己换工具），而不是直接失败
步数用尽 → 不带工具再问一次，强制作答（force-finish）
```

前两条是踩出来的：第一版只限制"轮数"，模型一次并行 3 个 call，5 轮跑出 12 步、
而且抓不到答案（返回空）。

## 实测（20 条 gold set，DeepSeek V4.1 Flash）

| 指标 | rules | loop |
|---|---|---|
| 答案通过率 | **100%** | 80% |
| 工具匹配 | **100%** | 90% |
| 平均工具调用 | **0.95** | 5.9 |
| 延迟 p50 | **1595 ms** | 8468 ms |
| 延迟 p95 | **6180 ms** | 12911 ms |
| 20 条成本 | **$0** | $0.0453 |
| tokens | 0 | 103,077 |

## 失败分析：4 条失败里有 2 条其实答对了

| 用例 | loop 的实际表现 | 判定 |
|---|---|---|
| refuse-quantum | 回答"没有找到研究 quantum gravity phenology 的专家，该组合在库中不存在" | 内容正确，但 `refused` 标志未置位 → 判失败 |
| refuse-poetry | 同上（明确列出检索过程与"不相干"结论） | 同上 |
| multi-turn-1 | 反问"请问'这些人'指的是哪一组？" | 行为合理，但不符合 gold set 的措辞要求（"上一批"） |
| multi-turn-2 | 同上 | 同上 |

**这是评测口径的问题，不是能力问题**：机械判定依赖两个契约——
`refused` 布尔标志、以及回答里出现特定措辞。模型用自然语言表达了同样的意思，就被判失败。

我试过加"散文拒答 → 标志"的映射（`_looks_refusal`），但模型每次措辞不同，
映射覆盖不全，仍然漏判。**结论：要么让循环输出结构化拒答，要么改判定标准**，两者都属于评测工程。

## 第二个发现：多轮上下文在循环里不稳

规则路径第一轮一定调 `find_expert`（会 `ctx.save`）；循环可能先调 `works`，
于是没有保存结果集，第二轮只能反问。

**根因**：上下文继承是"某个工具侧效应"，而不是模型的输入。
正确做法是把上一轮结果集**显式塞进 prompt**（"候选名单：pid 1,2,3…"），
而不是指望模型走对工具。这条没做，留作遗留。

## 结论

1. 在**闭域、固定问法、要求确定性**的场景，规则路径仍然全面占优（质量、延迟、成本、稳定）；
2. 循环的代价是明确的：**6 倍工具调用、5 倍延迟、$0.0023/条**；
3. 循环的价值不在这个 gold set 上（它测的是"已知问法"），而在**开放问法**——
   多跳、需要中途判断、规则覆盖不到的表达。这部分还没有评测集，是下一步。

**一句话**：这一轮没有推翻 m49，而是把它补完整了——
"路由用规则、worker 用模型"的混合架构，现在有了两端的实测数据。

## 遗留

1. 没有开放问题的评测集，所以"循环更泛化"目前是推测而非证据；
2. 多轮上下文没有显式注入 prompt（见上）；
3. 拒答契约不统一：循环应该输出 `{"answer","refused","reason"}` 结构化字段，而不是让判定去猜措辞；
4. 循环没有做工具结果的去重/压缩，token 消耗 10 万级里有一部分是重复证据。
