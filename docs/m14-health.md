# M14：数据健康度监控（把踩过的坑变成指标）

## 为什么做

前面 13 个里程碑里，我踩的坑几乎都是"数据悄悄坏了，但接口仍然 200"：

| 事故 | 当时的发现方式 | 代价 |
|---|---|---|
| 作者挂错论文（M11） | 用户看不出，我人工抽查合作者名单才撞见 | 829 篇论文关联全错，需要全量重建 |
| 网络背书占比失控（M13） | 我自己算了一下才发现定义写错 | 3,542 人被错误标记 |
| **FTS 漏索引（本次）** | 健康检查一上线就报出来 | **6,567 人搜不到** |

所以把这些检查固化成一个接口，而不是靠"下次记得查"。

## 接口

`GET /health/trust`：

```json
{
  "ok": true/false,
  "warnings": 1,
  "network_ratio": 0.028,
  "limit": 0.05,
  "checks": [
    {"name": "...", "label": "...", "value": ..., "limit": ...,
     "count": ..., "total": ..., "status": "ok|warn", "hint": "..."}
  ]
}
```

六项检查，每项对应一次真实事故或一条产品约束：

| 检查 | 限制 | 为什么 |
|---|---|---|
| 网络背书占发布集比例 | ≤ 5% | 超过说明在靠"和名人合作过"灌人，门槛该重新校准 |
| 无作者论文比例 | ≤ 5% | OpenAlex 侧的书/报告本来就没有作者；异常升高说明作者关联又错位了 |
| 重复 openalex_id | = 0 | UPSERT 误用 `lastrowid` 的副产品 |
| 悬空边（指向不存在的人） | = 0 | 合并人物后可能残留 |
| FTS 行数与人物数之差 | = 0 | 增量更新 FTS 时漏写会导致某些人搜不到 |
| 发布专家中无主题比例 | ≤ 35% | 过高会让主题筛选失效 |

前端顶部有橙色告警条（`ok=false` 时才出现），列出不达标的项和修复建议。

## 上线当天的战果

第一次跑就抓到：

```
⚠ FTS 行数与人物数之差  6,567   (41002 / 47569)
```

原因：`expand_author` 新建人物时只写了 `people`，没写 `people_fts`——
**M12/M13 扩张出来的 6,567 人，在搜索里根本不存在。**

修复：
1. `app/repair_fts.py` 增量补齐（不重建整表，秒级）；
2. `expand_author` 里补上写 FTS 的语句，防止下次再漏。

修完：

```
people 47569 / fts 47569  → 差值 0
搜索抽查：Kefang Lai(230 篇)、Pixin Ran(369)、Ruchong Chen(166) 都能命中
```

## 副作用（诚实记录）

FTS 多了 6,567 行，检索竞争进一步加剧，基线再次下降：

| 配置 | M12 后 | 现在 |
|---|---|---|
| bm25 | 0.1737 | **0.1687** |
| dense | 0.0645 | 0.0645 |
| rrf | 0.1880 | 0.1856 |

这不是退步，是"把之前漏掉的人加回索引"的必然结果。
**但从此以后，这类变化会被 `/health/trust` 和回归基线同时记录**，不会再静默发生。

## 一个仍未解决的判断

`network_endorse_ratio` 现在的上限 5% 是我拍的。
它的依据不是测量，而是"M12 发现 3,542 人（42%）时明显失控，238 人（2.8%）看起来合理"。
如果要把这个阈值做实，需要人工抽样判断"网络背书的人有多大比例是真的领域专家"——
这件事没做，所以报告里标注为**未经校准的阈值**。
