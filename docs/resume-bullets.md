# 简历条目（ScholarTrust）

> 用法：按岗位选一段。数字都可以在 `docs/m1-report.md` ~ `m5-report.md` 里找到出处。
> 公网地址：https://<public-url>

## A. 完整版（4 条，AI 应用 / 平台工程向）

**ScholarTrust：学术专家知识库 + 可信采集 Agent（个人项目，公网可访问）**

- 从 OpenAlex 公开 API 采集 **8,000 篇论文 / 36,083 位作者 / 88,558 条合作边**，构建专家知识库与
  合作图谱；设计 works-first 采集策略（1 次 API 额度 = 200 篇论文 + 数百作者），
  把 8000 篇的采集成本压到 **40 次请求 / 157 秒**。
- 检索层做 **BM25(FTS5, porter 词干) + bge-small-en 向量 + RRF/DBSF 融合**，
  自建两套 gold set（100 + 50 条），报告 Recall@10 / MRR / nDCG@10 与 **bootstrap 95% 置信区间**；
  实测 BM25 优于向量（0.243 vs 0.065），融合未赢过更强单路，**据此不启用融合**。
- 用**权威性先验**做重排时发现评测存在**标签泄漏**（真值按被引排序），
  于是另建"随机真值"对照组，验证先验在无偏真值上 **反而降低召回（0.243→0.214）并放弃**。
- 可信采集：结构化打分器（身份/产出/影响/归属四组权重）+ 置信分层 + 复核队列（带留痕），
  人工抽检 60 条发现**三档全是真人**——据此把门槛从"判是不是人"改成"筛产出"，
  单篇作者不自动发布；非人实体 17/17 被挡在发布集外。
- Agent：**LangGraph** 编排 5 个工具（找专家/画像/合作网络/论文/对比），带引用与拒答；
  用 cross-encoder 做拒答判定（阈值 0.60，实测可完全分开"有答案 0.858+ / 无答案 ≤0.425"），
  24 题评测工具选择/拒答/引用/结构化数字**四项全部 100%**。
- 工程化：SSE 流式、写接口 API Key 鉴权（fail-closed）、26 项安全加固、压测（检索 ~20 rps 饱和）、
  5 个里程碑报告与可复现脚本。

## B. 检索/算法向（4 条）

- 学术专家检索：BM25 + 稠密向量 + 融合三路，**自建两套 gold set**（按被引排序 / 随机抽样），
  用 bootstrap CI 判断差异显著性。
- 发现并修正两个"看日志看不出"的 bug：中文查询词进入 FTS 的 AND 条件导致**全空召回**；
  中文混写使 cross-encoder 打分从 0.999 稀释到 0.175 导致**误拒**。
- 指标：BM25 nDCG@10 0.243（无偏真值）/ 0.342（被引排序真值）；向量通道 0.065/0.166；
  融合 0.196/0.324 —— 结论是**融合不如更强的单路，故不启用**。
- 拒答：三个便宜信号（稠密相似度、BM25 分、覆盖率）都无法分开"有/无答案"，
  **只有 cross-encoder 可分**（0.858+ vs ≤0.425），据此定阈值 0.60。

## C. 后端/平台向（3 条）

- FastAPI + SQLite(WAL) + FTS5 单机部署：8 个接口（检索/画像/图谱/复核/Agent/SSE），
  DB 133MB，RSS 759MB（含两个 ONNX 模型常驻），检索并发 4 时约 20 rps。
- 安全：发现并修复**无鉴权写接口**（可投毒知识库）→ X-API-Key + fail-closed；
  关闭 /docs 与 openapi；验证 401/503/404 与异常输入无堆栈泄漏。
- 可复现：5 份里程碑报告 + 采集/评测/压测/审计脚本；单测 8 个。

## 面试可讲的三个"取舍"

1. **为什么不做融合**：融合只有在赢过更强单路时才值得；我们的数据是实体卡片 + 实体查询，BM25 天然占优。
2. **为什么门槛筛的是"产出"而不是"是不是人"**：采集走 authorship，源头就是人；
   真正要防的是"露过一次脸就当专家"。
3. **为什么用规则规划器而不是 LLM**：演示环境无可靠模型；五个意图用规则 100% 判准，
   且每一步可解释、可单测。LLM 合成是后续增强项，不是正确性前提。

## 面试会被追问、需要提前准备的点

- **重名合并没做**：同一姓名不同 ORCID 可能被合并成一个人。这是学术图谱最难的问题之一，我没有覆盖。
- **作者聚合较粗**：命中论文的所有作者按 CE 分求和，可能把"论文摘要里顺带提到"的人排上来。
- **评测规模小**：60 条人工抽样、17 条非人实体，CI 很宽，不能声称"总体精度 98%"。
- **单机单 worker**：~20 rps 是 SQLite 的限制，不是架构上限；换 PG 可继续扩。

## D. 增补（M6/M7 之后）

- **前端**：单文件 SPA（无构建），检索 / 专家画像 / 合作图谱(SVG) / Agent SSE 对话 / 复核队列五个页面，
  与后端同一进程托管，公网可访问。
- **chunk 级检索实验**：摘要级 28,405 块 → 全文级 53,300 块（396 篇全文：arXiv 覆盖 100%）。
  结论是**否定的**：在随机真值上 chunk 排序 0.031 vs 人物索引 0.240；
  只有换到"按被引排序的真值"才反超（0.207 vs 0.130）——
  这是我第四次识别出同类**标签泄漏**。最终把 chunk 定位为"句子级证据"而非排序通道。
- **抓全文中踩的坑**：OpenAlex `best_oa_location.pdf_url` 大面积为 null，必须扫 `locations[]`；
  `nature.com/*.pdf` 返回 HTML 拦截页，所以要校验 `%PDF` 魔数；高被引论文与付费墙高度重合，
  8000 篇里只有 5% 能拿到全文。
