# M58：库扩充的评测（自建缺口主题集 + A/B + 盲审）

## 先查公开数据集：没有能直接用的

| 数据集 | 内容 | 能否用 |
|---|---|---|
| [TREC Enterprise expert search](https://trec.nist.gov/pubs/trec15/papers/ENT06.OVERVIEW.pdf)（2006–2008） | 企业语料 + 主题 → 专家 | 语料不同源，无法迁移到我们的库 |
| [S2AND](https://dl.acm.org/doi/abs/10.1109/JCDL52503.2021.00029) | 作者同名消歧 | 是另一条能力 |
| BEIR scidocs/scifact | query → 论文 | 评"查论文"，不是"找专家" |
| [On the Biased Assessment of Expert Finding Systems](https://ar5iv.labs.arxiv.org/html/2410.05018)（2024） | 专家发现标注偏差 | **方法论参考**：标注者偏见会系统性抬高/压低分数 |

结论：**自建**。但金标不能来自被测系统自己的生成规则（否则循环论证）。

## 设计

### 缺口主题集（`app/build_gap_topics.py`）

不从已有 60 个概念里挑（那些本来就有人），而是：

1. 拉 OpenAlex 近期高被引论文（3 页 × 100），收集 `topics[].display_name`；
2. 过滤库里 published 人数 < 2 的主题（真正缺口）；
3. 金标池 = 这些论文的作者里，**OpenAlex 作者标签（x_concepts/topics）包含该主题**的人；
4. 池子 ≥ 5 人保留，固定种子采样 20 个 → `eval/gap_topics.jsonl`。

**金标用作者标签，不用标题匹配**——后者是我们的生成规则，不能既当运动员又当裁判。

### A/B（`app/eval_expansion.py`）

| 组 | 设置 |
|---|---|
| A | `ST_AUTO_EXPAND=0` |
| B | 默认（无相关专家 → OpenAlex 采集 → 重试） |

指标：回答率、检索命中（返回专家 ∩ 金标池）、新增人数、成本、延迟。
另生成盲审表 `eval/audit_sample.csv`：每主题抽 5 人，只给人名/机构/被引/代表作，**不给来源**。

## 第一次实测（6/20 主题，控制成本）

```
回答率：关闭扩充 67% → 开启 83%
新增专家：5 人（只有 1/6 主题扩出了人）
检索命中（OpenAlex 标签金标）：0 / 66
成本 $0.027 · p50 19.9s
```

### 三个诚实结论

1. **"标签缺口" ≠ "能力缺口"**：A 组回答率已经 67%——因为检索走标题/关键词匹配，
   即使库里没人带该主题标签，也能从论文标题命中。缺口主题要按"检索也答不出"来定义，
   而不是按"标签数=0"。
2. **扩充与金标用了不同信号**：扩充选人靠标题关键词，金标按作者标签，两边集合几乎不相交
   → 检索命中 0%。要让扩充命中金标，必须把**作者标签**也作为扩充的输入信号。
3. **长主题名难匹配**："Scientific Computing and Data Management" 这类主题即使放宽到
   "≥2 个关键词"也只能扩出 5 人；短病名（Gaucher disease）效果好得多。

## 过程中修的 3 个基础设施 bug

1. **OpenAlex API key 从未被发送**（`with_key` 定义了但没调用）→ 一直用全网络共享的
   $0.10 免费额度，额度耗尽就 401；
2. 401 时不会降级 → 整条流水线挂掉；现在自动切无 key 并重试；
3. 主题匹配只认完整短语 → 长主题名永远 0 候选；现在支持"≥2 个关键词命中"。

## 下一步（按价值）

1. 扩充时把 **OpenAlex 作者标签**作为第二信号（直接对齐金标）；
2. 缺口主题改为"检索 top-10 里没有该主题标签的人"（能力缺口，而不是标签缺口）；
3. 人工盲审 21 条样本，算精确率与 kappa（表已生成）；
4. 跑满 20 个主题 + 回归 60/14。

## 局限

- 6/20 主题，样本小；
- 盲审未标（CSV 已就绪）；
- 扩充是写库操作，A/B 的 B 组会真实改变库，重复跑需要清 `expansion_log`；
- 本次结果**不支持"扩充有效"的结论**，只证明了评测框架能暴露问题。

## 第二轮：接入作者标签 + 改成"能力缺口"

### 改动

1. **扩充加第二信号**：`_find_authors` 现在同时看
   - 信号 A（标题）：≥2 篇标题命中；
   - 信号 B（标签）：作者 profile 的 `x_concepts`/`topics` 含该主题。
   任一成立即算，并记录 `signals=label,title` 到 `expansion_log`。
2. **缺口定义改为能力缺口**：候选主题先用产品路径查一遍，**前 10 名里没有任何专家的
   标签匹配该主题**才算缺口（而不是"标签数=0"）。

### 又发现一个检索 bug

长主题串进 FTS 会被 `and/of/analysis/networks` 这类词污染：
"Bioinformatics and Genomic Networks" 会召回 **Hinton、Bengio**，
"3D Shape Modeling and Analysis" 会召回 SEM 学者。

修复：FTS 前剥通用词（`_fts_safe`），并在结果上要求**人物标签至少命中 2 个实词**。
修复后：
- 3D Shape Modeling → 诚实返回 **0**（库里确实没有）
- Bioinformatics and Genomic Networks → cBioPortal 团队（Schult/Gao/Cerami）
- Gaucher disease → 4 位脂质沉积病学者

### 第二轮 A/B（9 个能力缺口主题）

```
回答率：关闭 56% → 开启 78%
新增专家：27 人
检索命中（OpenAlex 标签金标）：0 / 91
成本 $0.041 · p50 42.9s
```

### 为什么命中还是 0

金标作者**几乎没进库**：抽查前三个主题，金标在库 0/10、0/12、1/10。
原因是扩充选人按"标题命中数 + 被引"排序，取前 5；金标池按"作者标签"构造，
两个集合在候选排序上不重合——**不是随机错，而是排序目标不同**。

### 代价与回归

| 指标 | 改前 | 改后 |
|---|---|---|
| 专家发现 R@10 | 88.7% | **85.5%**（-3.2pt） |
| 专家发现 R@5 | 52.9% | 50.5% |
| Agent 14 条 | 14/14 | **14/14** |
| Agent p50 | 8.8s | 6.4s（评测已隔离扩充） |

R@10 的下降是"标签关键词过滤"换来的精度：过滤掉噪声的代价是少数金标作者被误杀
（ex-14、ex-32 变成零命中）。这是**明确记录在案的取舍**，不是回归 bug。

### 下一步（仍未做）

1. 扩充排序改为**标签优先**（现在标签只用于准入，不用于排序）——这是把命中从 0 拉起来的直接手段；
2. 跑满 20 个能力缺口主题；
3. 人工盲审 21 条（表已生成），算精确率与 kappa；
4. 专家发现 R@10 的 -3.2pt 需要调过滤阈值（1 个关键词 vs 2 个）。

### 结论

评测框架已经能稳定暴露问题：**两轮下来发现了 4 个真 bug（key 未发送、FTS 污染、
缺口定义错、扩充排序与金标不一致）**，但没有得出"扩充有效"的结论。
如实记录比粉饰更有价值——这正是这套评测存在的意义。

## 第三轮：标签优先排序 + pending 状态 bug

### 改动

1. `_find_authors` 改为**标签优先**：先把作者标签命中主题的人全部挑出（按被引降序），
   不够再用"标题 ≥2 篇"的人补齐；候选池从 24 放宽到 40，默认扩容 8 人。
2. 修第 5 个 bug：**标签命中但标题 0 篇的作者被判成 `pending`**，
   所以"扩充了却检索不到"。验证条件从"标题命中≥1"改为"标签 或 标题命中"。

### 第三轮 A/B（9 个能力缺口）

```
回答率：关闭 67% → 开启 89%（+22pt）
检索命中（独立标签金标）：0% → 11.7%（gap-04 3/9、gap-05 4/8、gap-08 2/9）
成本 $0.047 · p50 75s（扩充要拉 40 个作者档案，慢）
```

**这是第一次拿到非零命中**：说明"标签优先 + 修正状态"确实让金标作者进入了可检索集合。

### 但代价很大（如实记录）

| 指标 | 基线 | 现在 | 变化 |
|---|---|---|---|
| 专家发现 R@10（60 条） | 88.7% | **80.9%** | **−7.8pt** |
| 专家发现 R@5 | 52.9% | 47.6% | −5.3pt |
| 覆盖 | 100% | 97% | −3pt |
| Agent 14 条 | 14/14 | 14/14 | 持平 |

尝试过的缓解（都没回到基线）：

1. 标签过滤从"≥2 关键词"放宽到"≥1"：82.7%（无效）；
2. 只对多词主题过滤：80.2%（无效）；
3. 单词概念查询排除 `auto_expand`：80.9%（无效）。

**尚未定位真正原因**。已排除：FTS 重复（`rows=47628 / distinct=47628`）、
过滤阈值、自动扩充作者。剩余假设：

- 扩充写入改变了 `people_fts` 的词频分布（bm25 的 IDF 变化），
  导致原有概念查询排序漂移；
- `_topic_experts` 候选池从 100 放宽到 200 后，排序尾部噪声进入前 10。

### 结论（必须说清）

- 扩充在**能力缺口**上确实有效：回答率 +22pt、命中从 0 到 11.7%；
- 但它**污染了原有概念查询**，R@10 掉了 7.8pt，且三个缓解手段都无效；
- 所以现在的系统还不能说"扩充是净收益"。**下一步应该先定位这 7.8pt 的来源**
  （重建 FTS 后重跑、以及把 auto_expand 作者整体暂时排除后再测），再决定是否默认开启扩充。

## 诊断实验：−7.8pt 到底来自哪里

用两个开关跑 2×2 矩阵（专家发现 60 条）：

| 配置 | R@5 | R@10 | MRR |
|---|---|---|---|
| 现状（池 200，含 auto_expand） | 47.6% | 80.9% | 0.849 |
| 排除 auto_expand | 49.0% | 83.0% | 0.868 |
| 池 100 | 48.1% | 81.9% | 0.858 |
| **池 100 + 排除 auto_expand** | **49.5%** | **84.0%** | **0.876** |

结论：

1. **自动扩充的人是主要来源**（−2.1pt）：它们进了 `people_fts`，参与原有概念查询的竞争；
2. **候选池 200 是次要来源**（−1.0pt）：放宽后尾部噪声进入前 10；
3. 两者都关掉仍只有 84.0%，与基线 88.7% 差 **4.7pt**。
   剩余差异无法用开关解释，最可能是**新增文档改变了 FTS 的 bm25/IDF 统计**
   （FTS5 的统计是动态的，加文档就会漂移）——这不是 bug，而是增量写库的固有代价。

## 据此定的默认策略

| 项 | 默认值 | 理由 |
|---|---|---|
| `ST_AUTO_EXPAND` | **0（关闭）** | 净收益未确立，且会拉低原有概念查询 |
| `ST_TOPIC_POOL` | **100** | 比 200 更稳（+1.0pt）且更快 |
| 手动扩充 | `POST /library/expand` | 需要时显式触发，不进默认链路 |

**能力缺口的 +22pt 回答率仍然成立**——只是它不该以牺牲原有能力为代价。

## 仍未解决

- 4.7pt 的 IDF 漂移没有修法（可选：定期全量重建 FTS + 用固定 baseline 监控）；
- 自动扩充若要重新默认开启，需要先做到"扩充作者不参与非相关查询"的隔离（例如独立索引/独立打分通道）；
- 盲审表仍未标注（`eval/audit_sample.csv`）。

## 第四轮：按"独立索引"隔离（采纳外部评审意见）

外部评审（Claude）指出三点，我接受：

1. **FTS5 的 bm25 用整张虚拟表的统计量，加 `source` 过滤改不掉漂移**——必须物理隔离；
2. **4.7pt 在 60 条上 ≈ 1 个标准误，不能当根因结论**；应先做配对检验；
3. **+22pt 只是 9 条里 2 次翻转（McNemar p=0.5）**，收益侧与成本侧都不可测。

### 改了什么

- 新增 `people_fts_exp` 影子索引：自动扩充作者只写这里，**主索引 `people_fts` 只含发布集**；
- 检索顺序：主索引召回 → 若"相关结果不足"（< limit/2）→ 查影子索引 → **RRF 合并**（按排名，免疫分数不可比）；
- 迁移已有数据：**85 位 auto_expand 作者**从主索引搬到影子索引；
- 逐 query 结果现在落盘（`--save-rows`），新增 `app/paired_test.py`（精确 McNemar + 配对 bootstrap）。

### 配对检验（60 条，同一批 query）

| 对比 | ΔR@10 | 95% bootstrap CI |
|---|---|---|
| 隔离后 vs 隔离前（含扩充） | **+3.17pt**（80.9% → 84.0%） | **[0.3, 6.7]** |
| 过滤门槛提到 ≥3 实词后 | +3.00pt（80.9% → 83.9%） | [0.3, 6.3] |

**McNemar 在该口径下无判别力**：两边对每条 query 都至少命中一个金标，
不一致对 = 0/0，p=1.0。这说明"命中/未命中"的二值口径太粗，应改用连续指标（bootstrap）。

### 必须承认的两点

1. **之前"IDF 漂移"的归因撤回**：基线（88.7%）的逐 query 结果当时没落盘，无法回溯检验；
   现有证据只能支持"隔离带来 +3.0pt"，不能支持"剩余 4.8pt 来自 IDF"。
2. `ex-14`、`ex-32` 仍零命中：金标作者都在主索引、状态 published，
   过滤门槛放宽到 ≥3 实词也没恢复——**原因未明**，记录为未解问题，不再猜。

### 当前默认

| 项 | 值 |
|---|---|
| 主索引 | 仅发布集（47,569 人），分数可复现 |
| 影子索引 | 85 位 auto_expand 作者，仅在主检索不足时启用 |
| `ST_AUTO_EXPAND` | 仍默认 0（隔离已完成，但净收益仍需 40 条缺口主题验证） |
