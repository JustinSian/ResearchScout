# M17 规划：从「检索 + 单轮 Agent」升级到「专家尽调 Agent Harness」

## 为什么改方向

对标一份真实简历里的 Agent Harness（任务规划 / 虚拟文件系统 / 子 Agent / 上下文管理 /
中间件 / Skills / 记忆 / 沙箱 / 链路追踪），我们现在的差距不是"模型"，是**工程骨架**：

| 能力 | 现状 | 差距 |
|---|---|---|
| 任务规划 | 单轮规则出 1 个工具调用 | 无多步、无状态机 |
| 虚拟文件系统 | 无 | 大结果直接进上下文 |
| 子 Agent 委派 | 无 | 所有事在一个上下文里做 |
| 上下文管理 | 无压缩 | 长结果塞满 prompt |
| 中间件/Hook | 只有 API Key 鉴权 | 无审计/限流/成本核算 |
| Skills | 规则写死在代码 | 换策略要改代码 |
| 记忆 | 有表，Agent 不读写 | 无跨会话复用 |
| 沙箱 | 无 | 不能算指标 |
| 链路追踪 | 无 | 只能翻日志 |

## 新定位：不做通用助手，做「专家尽调 Agent」

选择理由：尽调是有明确步骤、可验收、且**正好卡在我们数据上**的任务。

```
输入：一位专家（或一篇论文）
→ 拉全量成果（dossier）→ 判别代表作 → 算画像（h-index/主题迁移/合作圈）
→ 交叉验证（机构一致性 / 同名合并 / 异常年份）→ 找利益冲突（共同作者/同机构）
→ 出尽调报告（每条结论带证据）
```

## 技术规划（问题 → 技术 → 指标）

| # | 问题 | 技术 | 指标 |
|---|---|---|---|
| 1 | 单轮答不了"两位专家谁更适合审这篇稿" | 任务规划 + 状态机（≤6 步） | 多跳成功率、平均步数、死循环率 |
| 2 | 一位专家上千篇论文塞不进上下文 | 虚拟文件系统 `/dossiers/{pid}/*.jsonl` | 上下文 token 峰值、可处理论文数 |
| 3 | 检索/核算/校验需要不同工具集 | 子 Agent：researcher/analyst/verifier/critic | 子结论 token 占比、子任务成功率 |
| 4 | 长任务遗忘 | 滚动摘要 + 事实表（entity→fact） | ≥8 轮完成率 |
| 5 | 谁调了什么、为何拒答查不到 | 中间件 + span（trace_id/step/tool/latency） | 可回溯率、p95 归因 |
| 6 | 策略散在代码里 | Skills（Markdown 加载） | 改策略不改代码、A/B 命中率 |
| 7 | 重复尽调同一人 | 记忆：dossier 缓存 + 变更 diff | 二次耗时下降、变更召回 |
| 8 | 需要算 h-index/网络指标 | 受限代码执行（subprocess + 白名单） | 计算正确率 |
| 9 | 结论无法复核 | 引用强制 + verifier | 引用覆盖率、无证据结论数=0 |

## 数据规划：100 位专家 × 全量成果

已建 `dossier` / `dossier_work` 两张表 + `app/build_dossiers.py`。

试点（已跑通）：

| 专家 | 全量论文 | h-index | 被引合计 | 年份跨度 |
|---|---|---|---|---|
| Ahmedin Jemal | **1,096** | 173 | 742,394 | 1993–2026 |
| Rebecca L. Siegel | **277** | 92 | 566,073 | 2006–2026 |

对比：改造前库里这两位分别只有 35 / 29 篇。

成本：每位 2~6 次请求（按 200 篇/页）；100 位 ≈ 300~600 次。
OpenAlex API key 已申请（`your-email@example.com`），**激活后 $1/天 = 1 万次**，一次跑完没问题。

## 待定：100 位怎么选

| 方案 | 特点 | 适合 |
|---|---|---|
| A 全网被引 top-100 | 跨学科（癌症/物理/蛋白组学），数据最全 | 展示"数据处理能力" |
| B 钟南山/李兰娟网络内 top-100 | 同一领域、互相连通，图谱好看 | 展示"领域深耕 + 网络分析" |
| C 某学术图谱 483 名单里的 100 位 | 与对标项目同源，可对比 | 展示"和对标项目的差异" |

推荐 **B**：尽调报告之间能互相对照（"A 和 B 共同署名 12 篇"），图谱也能连成片。
