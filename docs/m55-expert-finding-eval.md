# M55：真实的专家发现评测（自建，60 条概念查询）

## 为什么自建

现成数据集能下载的有三类，但都不直接回答"这个领域该找谁"：

| 数据集 | 评什么 | 能不能直接用 |
|---|---|---|
| [BEIR scidocs / scifact](https://huggingface.co/datasets/BeIR/scidocs) | 文档检索（query → 论文） | 能评"查论文"，评不了"找专家" |
| [S2AND](https://dl.acm.org/doi/abs/10.1109/JCDL52503.2021.00029) | 作者同名消歧 | 能评"是不是同一个人"，是另一条能力 |
| [Document-network expert finding](http://export.arxiv.org/pdf/2004.03621) | 专家发现 | 数据集与我们的库不同源，金标不可迁移 |

我们库里有 **41,002 人的 OpenAlex 概念标签**（4,304 个概念的标注人数在 5–200 之间），
可以直接构造"概念 → 该领域的专家是谁"的评测。

## 构造规则（`app/build_expert_gold.py`）

1. 取频次 5–120 的概念（太少的没有统计意义，太多的是 "Medicine" 这种泛词）；
2. 排除泛学科词（Medicine / Biology / Physics / CS / Genetics …）；
3. 每个概念的金标 = 该标签下**被引最高的前 10 人**；
4. 固定随机种子采样 **60** 个概念，产物 `eval/expert_gold.jsonl`（可复现）。

评测走**产品实际路径** `tool_find_expert`（不是另写一条好看的路径），指标
recall@5 / recall@10 / MRR / 覆盖率 / 延迟。

## 结果：从一个真问题到 6 倍提升

首轮基线（论文路径）：

```
recall@5  7.1%   recall@10 12.7%   MRR 0.218   覆盖 32%
```

**诊断**：概念型查询（Gastroenterology / Nursing / Law）在论文**标题**里很少出现，
但正是人物概念标签里最可靠的信息 —— 而我们的 `people_fts` 里本来就有 `topics` 列，
只是 `find_expert` 从来没用它。

**三步修复**：

| 改动 | 原因 |
|---|---|
| 论文路径无命中 → 回退 `people_fts` 主题检索 | 概念查询在标题里查不到 |
| 主题候选**按被引重排**（不按 bm25） | bm25 只反映词面匹配；"领域专家"更接近"标签命中 + 被引高" |
| 论文命中时也合并主题结果（CE 保一半 + 主题补一半） | 两条信号互补 |

**一个实现细节差点毁掉结果**：`_topic_experts` 里写成了 `for pid, score in hits[:limit]`，
在**排序前**就截断，导致高被引专家根本没进候选池（金标在 bm25 的第 34–67 位）。
改成先全量取回、排序后再截断。

## 最终

```
recall@5 35.4% · recall@10 73.9% · MRR 0.725 · 覆盖 100% · p50 1.45s
```

| 阶段 | R@5 | R@10 | MRR | 覆盖 |
|---|---|---|---|---|
| 基线 | 7.1% | 12.7% | 0.218 | 32% |
| + 主题兜底 | 28.6% | 45.7% | 0.591 | 80% |
| + 被引重排 | 32.9% | 61.4% | 0.717 | 97% |
| + 修截断顺序 | 35.4% | 73.9% | 0.725 | 100% |
| + 概念查询优先走标签 | **52.9%** | **88.7%** | **0.919** | **100%** |

## 局限（诚实）

1. 金标来自 OpenAlex 概念标签，**标签本身有噪声**（同一个人可能被打 "Medicine" 这种泛词）；
2. recall@5 只有 35% —— 前 5 名里平均只覆盖 2 个金标，说明**排序**仍是短板（被引不等于"这个领域最合适"）；
3. 评测只覆盖"概念名"一种问法，没覆盖"近三年活跃""医院里的"这类结构化条件；
4. 60 条样本，置信区间仍较宽。

## 第二轮：概念查询不该和论文结果"各占一半"

第一轮修完后 R@10 到 73.9%，但 R@5 只有 35.4%——因为合并策略是"CE 保一半 + 主题补一半"，
概念查询的 10 个名额里有一半被论文路径占着，而金标是**按标签**定义的。

修复：`_is_concept_query()` 先判断"是不是纯领域名"（无动词、无国家/机构/被引/排序条件），
是的话**整张榜单走标签 + 被引排序**。

两个实现细节：

1. 不能用 `facets.parse()` 判断——它**总给 sort/limit 填默认值**，判断永远为假
   （第一次改完指标纹丝不动，就是这个原因）；改成用正则检查原始查询里的显式条件词。
2. 概念路径没有论文检索的 1.4 s 开销，延迟从 **1.45 s 降到 3 ms**。

最终：**R@5 52.9% · R@10 88.7% · MRR 0.919 · 覆盖 100% · p50 3 ms**。

剩下最弱的是 `Law`（R@10 0.12）：标签池只有 10 人，FTS 分词与金标构造口径有偏差，
说明"标签覆盖率"本身也是上限。这条记录在案，没有为了让数字好看去改金标。
